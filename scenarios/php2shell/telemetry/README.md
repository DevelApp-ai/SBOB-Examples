# Telemetry (scenario B: PHP2Shell)

SBOB-EXAMPLES DEMO WATERMARK — scenario B telemetry captures. Demo
reconstruction, loopback-only stand-ins (TDS §4).

This directory documents the capture contract; the captured windows
themselves are per-run CI artifacts (the lane can never push to the repo),
and the committed evidence lives in `docs/php2shell/detection-evidence.md`.

## What is captured

`harness/run-behaviors.sh` (inside the disposable workload container) opens
two auditd windows:

| window | request | expected telemetry |
|---|---|---|
| `benign.audit` | `benign.php` | declared behavior only: `/var/www/html/*` read, `/var/lib/php/sessions/*` write, `/etc/resolv.conf` read, connect to the declared memcache peer `10.96.100.10:11211`. Must stay silent against the transpiled rules: level-0 base chain only. |
| `drift.audit` | `behaviors.php` | the four post-exploit behaviors: `/bin/sh` exec from the worker (CVE-2026-109618 follow-on), webshell drop to `/var/tmp/.php2shell.php`, C2 stand-in connect `127.0.0.1:4444` (CVE-2026-109619, loopback stand-in), `memfd_create` via FFI. |

Each window contains the same record types as the recorded corpus
(`type=SYSCALL`, plus the `type=EXECVE` / `type=PATH` / `type=SOCKADDR`
records of the selected event ids), so the files replay through the same
decoder chain.

## Capture scoping (why the windows are clean on a shared CI node)

The audit fragment is generated by `sbobctl transpile` from the SBoB
php contract, and its rules carry the scoping:

- `sbob-exec-php-fpm` / `sbob-open-php-fpm` / `sbob-connect-php-fpm` are
  **exe-scoped (Mode A)**: only processes whose exe is
  `/usr/local/sbin/php-fpm` trip them. The CI runner's own processes
  (docker, shell, node) never match, by construction.
- `sbob-memfd` (and the other signature keys) are **node-scoped (Mode B)**
  by design: every process on the node trips them. A CI runner node is a
  shared node, so `harness/capture-window.sh` attributes signature-key
  events to the workload by `uid=33` (the php-fpm worker uid, the same uid
  the recorded corpus carries). This is exactly the attribution that
  `rulePolicies.processAllowed` exemptions provide in a real deployment.
- `type=CWD` / `type=PROCTITLE` records are dropped: no sbob decoder or
  rule consumes them, and the recorded corpus carries only the four record
  types above.

## Safety assertions (TDS §4 hard rules, enforced twice)

1. In-container pre-check (`run-behaviors.sh`): every captured `SOCKADDR`
   must decode to `10.96.100.10:11211` or `127.0.0.1:4444`.
2. Runner-side parity checker (`harness/check_capture.py`): the same
   assertion, plus benign-window purity (declared paths only) and the
   presence of all four drift signatures with corpus-shaped fields.

The real PHP2Shell C2 (`45.155.148.12:4444`) is never contacted; the loopback
stand-in carries the same port, and the safety checker rejects any other
destination outright.

## Run artifacts

`php-detection.yml` uploads both windows plus the raw audit-log slice as a
workflow artifact per run; the committed evidence
(`docs/php2shell/detection-evidence.md`) cites the first green run.
