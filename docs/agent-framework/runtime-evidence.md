# M3 runtime-detection evidence (scenario A, issue #4)

SBOB-EXAMPLES DEMO WATERMARK — evidence document for the layer-2 runtime
detection lane (`.github/workflows/runtime-detection.yml`). This file states
the facts the lane asserts, including what the layer honestly does NOT
catch. Verdict stamps are committed below once the lane's first green run is
reviewed.

## The layer's premise

The consumer commits the workload contract — `sbobs/workload/
python-ci-runner.yaml`, a Python CI runner using agent-framework — and
transpiles it (`sbobctl transpile`, pinned SBoB toolchain) into Wazuh
detection artifacts + Sigma rules. On the runner, the transpiled audit
fragment tags the workload's syscalls (Mode A, exe-scoped to the declared
interpreter); the Wazuh rules decide drift. During the 2026-11-17 hijack,
the FIRST Python start after the malicious release was installed would have
fired alerts minutes after install: not on the next CVE scan, not gated on
any test reachability.

## The consumer contract (and its honest scoping decisions)

| Section | Declared | Why |
|---|---|---|
| execs | `/usr/local/bin/python3.12` | the interpreter is the only exec a test runner makes |
| opens | `/usr/local/lib/python3.12/site-packages/*` (read) | an interpreter start imports whatever is installed; path-level opens cannot see module semantics, so the `.pth`-triggered `_telemetry` import itself is NOT drift (the TDS §9.4 blind spot, restated at the path layer) |
| opens | `/home/runner/work/demo/*` (read/write) | the repo checkout + pytest cache. ONLY the checkout is declared: the runner's `_temp` token tree lives outside it, so the 1.26.2 runner-path token read is drift |
| opens | `/etc/resolv.conf` (read) | the standard resolver declaration (SBoB repo convention) |
| egress | `cluster-dns` 10.96.0.10:53/UDP | the only DNS path: resolving the exfil domain rides the DECLARED resolver and alerts nothing (TDS §9.3 DNS-blind limitation) |
| egress | `internal-pypi-mirror` 10.96.100.20:443/TCP | CI pulls packages from the org mirror |
| undeclared | the loopback sink (standing in for `webhook[.]site`), every credential path, `/proc/*/environ` | the drift surface: a test runner has no business with any of them |

Registry namespace: `sbobs/registry.yaml` (this repo's own; slot 2, rule
band 1002xx). Slot choice is recorded there: slot 0 collides with the stock
wazuh 4.14.6 example rule 100001, slot 1 is php-fpm's band in the upstream
registry.

## The corpora (`scenarios/agent-framework/telemetry/`)

Synthetic auditd lines in the reconstruction's observer model (Mode A keys
`sbob-{exec,open,connect}-python-ci-runner`), synthetic inode/pid/timestamp
fields; every path mirrors the M1 reconstruction's actual collection lists.
Corpus-to-rule expectations were verified on a local wazuh-manager 4.14.6
replica before the first lane run (`analysisd -t` clean; benign zero;
drift 100221×7 + 100231×1; sustained 100222 + 100232).

- `benign.audit` — clean 1.26.0 on the runner: interpreter exec, import
  reads, checkout read/write, resolv.conf, DNS + mirror connects. Expected:
  level-0 base chains only, ZERO drift alerts.
- `drift.audit` — first interpreter start after the malicious install: the
  `.pth` import (declared, quiet), 2 environ reads, 4 credential files, the
  runner `_temp` token (1.26.2 addition), the exfil-domain DNS query (via
  the declared resolver, quiet), the single POST to the sink. Expected:
  `100221`, `100231`.
- `sustained.audit` — 8 rounds of the drift families in one session.
  Expected: `100222`, `100232`.

## Honest absences (asserted as verdicts — the finding is the point)

1. **Exec drift (100211) stays quiet.** The stealer lives INSIDE the
   declared interpreter (fork + `os.setsid()`/daemon thread, no execve).
   Unlike PHP2Shell, where the shell exec fires, scenario A drifts only on
   opens and connect. Mode A exe-scoping keys the malicious process
   correctly here precisely because the interpreter itself is the
   compromised executable.
2. **The sensitive-file overlay (100201) stays quiet.** The stealer's cloud
   credential set (`.azure/`, `.npmrc`, `.git-credentials`, runner tokens)
   is NOT on the sensitive-file watchlist (shadow/sudoers/`.ssh/`/`id_rsa`).
   Each read still fires the plain open-drift rule 100221, but never the
   level-12 capability alert. This is the same credential under-weighting
   M2 recorded as finding 3 (`docs/supply-chain-evidence.md`), now observed
   at the detection layer: the cloud-credential watchlist ask needs the
   SBoB roadmap too.
3. **The DNS leg is blind by design.** Resolving the exfil domain rides the
   declared resolver — no drift signal on the query itself; the CONNECT to
   the resolved sink IP (100231) is what alerts (TDS §9.3).
4. **Sustained egress (100232) is a capability proof, not an incident
   replay.** The real stealer connects EXACTLY ONCE (single-POST, silent
   failure, no retry). 100222 (sustained collection), conversely, is
   realistic: the collector cap is 60-80 files in seconds.

## Lane shape

Single job: profile gate (validate + transpile wazuh + sigma) -> disposable
wazuh-manager 4.14.6 (hardened install: `analysisd -t` zero errors/warnings,
anchored `is running` grep, every generated CDB list declared in
ossec.conf, `--ulimit nofile` + `SYS_RESOURCE` runner flags) -> corpus gate
(wazuh-logtest, three corpora, expected ids + asserted honest absences) ->
sigma gate (sigma-cli 4.0.0, `sigma check` on every generated rule). All
verdicts surfaced as `::notice` annotations + step summary; lane never
stays red (TDS §7).

## Findings — what scenario A exposes at this layer (the gap map)

1. The credential-read mass that M2's diff ladder under-weights (+1 per
   path, advisory-not-mandatory) is caught HERE as per-line level-9 alerts
   — but the level-12 capability escalation (sensitive-file overlay) never
   fires, because cloud credential files are not on the watchlist.
2. The `.pth` import itself is invisible at the path layer: an interpreter
   start importing installed code is declared behavior. The observable
   drift begins at the first undeclared open — one syscall later.
3. A consumer who declared a wider workspace glob (or the whole HOME)
   would have pre-approved the credential reads into the contract. Profile
   tightness is load-bearing; no toolchain rule catches profile mistakes.
4. fork/setsid escape (the detach) produces no execve: the process-execution
   leg of this layer has nothing to say about in-process daemonization.
   Only opens + connect speak, which they do within seconds.
